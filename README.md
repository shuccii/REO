# Re.O(レオ)

Re.O は research-dev-orchestrator の略です。

**論文・修論の根拠を点検し、模擬質疑まで支援する研究アドバイザー**です。Claude Code と Codex で使えます。

- 主張ごとに根拠を対応させ、代替の説明と、必要な追加検証を示します。
- 指摘には、重大さ、修正案、「修正できたと判断する条件」を付けます。
- 発表前の模擬質疑では、一問ずつ質問し、答えに応じて追加の質問をします。
- 工学、生物、化学、物理、材料、情報など、分野ごとの確認項目と確認ツールを持っています。

実際の出力は [出力見本](docs/EXAMPLE.md) を見てください(架空の修論の抜粋を点検した記録です)。

> 試用版です。出力は助言であり、指導教員の判断や承認、提出の可否の代わりにはなりません。

### 初回の実行

1. 研究の分野・手法・段階を登録します。Claude Code か Codex で「Re.O の初回設定をして」と頼むと、`setup-profile` スキルが数問だけ質問し、`~/.config/reo/profile.md` に保存します。
2. 点検したい原稿のあるフォルダで、たとえば「draft.md を指導教員の立場で点検して。主張と根拠の対応、代替の説明、必要な追加検証を、重大な順に」と頼みます。

初回設定をしなくても使えます。その場合は、原稿の内容から分野と段階を推定し、推定したことを出力の冒頭に書きます。

## 段階に合わせた点検

学生実験レポート、輪講、卒論、修論・学会発表、論文執筆、研究の立ち上げで、求める水準を変えます。たとえば卒論に論文並みの新規性は求めません。ただし、計算の誤りやデータの漏れ、根拠のない主張は、どの段階でも指摘します。基準は `skills/research-review-workflow/references/phase-expectations.md` にあります。

## 対応する分野

工学、生物、化学、物理、材料、情報・数理、医学・薬学、地球・環境など、理系の幅広い研究に使えます。分野ごとの確認項目は `skills/research-review-workflow/references/probes/` にあり、初回設定で自分の分野に合うものだけを読みます。

| 分野・手法 | 確認項目 |
|---|---|
| 材料物性、データ同化、ベイズ最適化 | `materials-ml.md` |
| 生物・医学・ウェット実験 | `bio-experimental.md` |
| 化学合成・分析 | `chemistry-synthesis.md` |
| 物理・機械・電気・土木などの工学測定 | `physics-engineering.md` |
| 数値シミュレーション・理論 | `simulation-theory.md` |
| フィールド調査・疫学・社会調査 | `field-observational.md` |

## 分野別の確認ツール(任意)

`tools/` に、結果を JSON で返す確認用のスクリプトがあります。使う分野のものだけ入れてください(Python 3.11 以上)。

```bash
uv venv .venv
uv pip install -r requirements/base.txt      # 共通
uv pip install -r requirements/chem.txt      # 化学(RDKit)
uv pip install -r requirements/bio.txt       # 生物(Biopython)
```

| ツール | 確認すること | 必要なもの |
|---|---|---|
| `tools/dimcheck.py "F = m*a" --units "F:N,m:kg,a:m/s**2"` | 式の両辺の次元(単位)がそろっているか | base |
| `tools/uncertainty.py "m / V" --var "m=12.31:0.02,V=4.52:0.05"` | 誤差の伝播と、報告する桁 | base |
| `tools/power.py --effect 0.5 --power 0.8` | 必要なサンプルサイズ、検出力 | base |
| `tools/multiplicity.py --p 0.01 0.04 0.03` | 多重検定の補正(FDR など) | base |
| `tools/smiles_check.py data.csv --split-column split` | SMILES の誤り、重複、学習・評価データ間の分子と骨格の重なり | chem |
| `tools/sequence_identity.py train.fasta test.fasta` | 学習・評価データ間で配列が似すぎていないか | bio |

終了コードは 0 = 問題なし、1 = 問題あり、2 = 入力の誤りまたはパッケージ未導入です。ツールの結果は入力に対する計算であり、測定や主張そのものの正しさを保証するものではありません。

## スキル一覧

### `research-review-workflow`

- 研究監査、修士論文・論文の建設的査読、中間・最終発表の模擬試問、研究計画の評価
- 研究意義・新規性・論理・設計・データ・統計・材料科学・再現性・説明・倫理の10観点を確認
- 主張と根拠の対応、反証・代替説明、指摘の重大性と確度、修正案と解消条件を記録
- Webの一次資料、利用可能なSlack/Notionの原文を読み、取得範囲・知識の不足・未確認を明示
- 材料科学、データ同化、多忠実度、ベイズ最適化について必要な場合だけ専門的な確認を追加
- 模擬試問は回答を待ち、回答内容に応じて追質問する
- 私的な研究室情報は作業領域の `RESEARCH_REVIEW_CONTEXT.md` から参照し、配布物には同梱しない

使用例: 「修士論文を監査して、主張ごとの根拠・代替説明・必要な追加検証を示して」「この中間発表について、一問ずつ質問して回答に応じて追質問して」「研究計画の目的・方法・達成条件・実行可能性を評価して」。

### `thesis-defense-workflow`

修士論文の執筆・最終発表・口頭試問の準備を、発表日から逆算して進めるための手順です。理系大学院生向けで、NAIST の公開情報(審査基準6項目、マイルストーンとキャップストーン、審査スケジュール)を含みます。

- 事実の確定: 日程・持ち時間・提出物・現行基準・見られるルーブリックを公式資料で確かめ、確認できないものは「未確認」として指導教員に聞く項目にする
- 逆算の工程表と、全トラック共通の課題ログ(出どころ・重大度・完了条件)
- 4つのトラック。必要なものだけ読む
  - W 執筆: 問いと答えの対応、見出しから書く、結論先行、一文一義、比較条件の漏れ・重複の点検。既定では本文は本人が書き、AI は点検する。指導教員と AI 利用の範囲を合意した場合だけ「AI 下書きモード」を使える: 本人の結果・メモだけから下書きし、数値・引用はすべて出どころをたどり、段落ごとに本人が書き直して確認印を付け、段階式点検と「本文を見ずに説明する」確認を通す。AI の使用は記録して開示に備える
  - S スライド: 目的 → 結論 → 必要最小限の結果 → 方法の順に逆向きに設計、時間配分、ページ番号、予備スライド(手法の原理など)、展望
  - Q 質疑: 論文と審査委員の公開情報から想定質問を作る。はい/いいえを先に答える、聞き返す、知らないことは作らない、限界は事実として認める
  - R 研究レビュー: 段階式で行う。論文の骨格(見出し・各段落の第1文・図表キャプション・強い主張語・長すぎる文)を `scripts/thesis_skeleton.py` で1回だけ抽出して全トラックで使い回し、骨格上の安い点検(T1〜T7)を先に済ませ、落ちた箇所と中心の主張だけ本文を精読する(図 F1〜F6、方法 M1〜M6、データ駆動 D1〜D5、解釈・倫理 I/E)。中心の主張は `research-review-workflow` で監査し、模擬試問をする。点検は省かず、精読の範囲を絞って時間と使用量を減らす
  - 想定質問は、修論発表会の質疑の実証研究(質問は方法・過程の条件・解釈に集中し、1問が平均約5往復の連鎖になる)を踏まえ、少数の質問に深い追質問の連鎖を用意する
- 計時つきリハーサルの記録、当日のチェックリスト、発表後の修正とデータ保存
- 提出・アップロード・教員への連絡はせず、合否の予測もしない

使用例: 「修論発表まで10週間。工程表と課題ログを作って」「この草稿を執筆チェックにかけて」「スライドを逆向き設計の観点で点検して」「この論文と審査委員の公開情報から想定質問を作って、一問ずつ練習させて」。

正式な監査レポートの構造検証:

```bash
python3 -B scripts/validate_research_review.py --json review-report.json
```

この検証は宣言された根拠の参照関係や状態の整合性を点検するもので、科学的正しさ・教授と同等の能力・学位合格を保証しません。原データ・実行環境がない文書レビューは、数値的妥当性を未評価として完了できます。実験の実行や科学的結果の統合には、従来の `research_strict` 契約と独立レビューを引き続き使います。教員承認・提出許可は別に扱います。

### `setup-profile`

- 分野・手法・段階・所属大学を数問で聞き、`~/.config/reo/profile.md` に保存する
- ほかのスキルは作業の最初にこのファイルを読み、分野に合う確認項目と段階に合う水準を選ぶ
- 学籍番号・住所・研究室規程の本文などは保存しない

### `research-ml-workflow`

- `research_strict` プロファイルによる研究・分析向けの厳格な検証
- グループ単位の分割、学習データ内での前処理、リーク検査
- 生予測値、反復・シード間のばらつき、不確実性の記録
- 検証に失敗した場合の下流成果物・主張の無効化
- 予測上の関連と因果的解釈の分離

### `lab-policy-workflow`

- ローカル登録された研究室規程を、著者・貢献整理、学会参加計画、要旨・ポスター・口頭発表準備へ適用
- 作業領域の `AGENTS.md` と、必要に応じ `~/.config/reo/lab-policies.md` から適用対象を解決
- 規程本文・原本PDF・個人の参照パスはプラグインに同梱せず、研究室ごとの適用範囲を維持
- 教員確認・発表練習・承認状態と、ユーザーの提出・送信許可を区別

この機能はローカル設定を参照するワークフローであり、教員承認を取得・代行する機能ではありません。他の環境で使う場合は、その環境に適切な規程と参照先を登録してください。

### `root-cause-debugging`

- 実行エラーや NaN・不安定な計算を、再現 → 正常例との比較 → 仮説1つと最小の検証 → 原因への修正の順で調べる
- 無断のデータ除外・NaN置換・都合のよいseed選択で症状を隠さず、判断と影響を記録
- 修正が3回効かなければ現在の修正ループを止め、前提と計画を見直す。既存の研究検証・独立レビューは維持

### `orchestrate-work`

- 複数の作業ストリームを整理し、依存関係と担当範囲を明確化
- 必要な場合だけ並列作業を使い、独立したレビューを記録
- 機械可読なタスクマニフェストと結果を用いて、検証済みの成果だけを統合
- 公開、提出、送信、デプロイなどを承認が必要な操作として扱う

## 研究タスクでの基本方針

研究・機械学習では、次の順序で確認します。

1. 研究質問、目的変数、独立単位、許可されたデータソースを定義する
2. 分割単位と評価指標を固定する
3. 前処理・特徴量選択・補完・リサンプリングを学習データ内で実行する
4. 生の予測値、設定、シード、ログ、生成物を保存する
5. 独立レビューでリーク、指標、解釈、再現性を確認する
6. 根拠の範囲を超える因果・一般化・性能主張を避ける

未実行の計算、取得できないデータ、検証待ちの値は、結果として扱わず制約として明示します。

## 開発者向け

```bash
git clone https://github.com/shuccii/REO.git
cd REO
python3 scripts/run_checks.py
```

テストは、スキルの構成、JSON の契約、確認ツールの計算を点検します。確認ツールのテストは、必要なパッケージが入っていない場合は飛ばされます。テストが通っても、研究支援の質が保証されるわけではありません。

```text
.
├── .claude-plugin/   # Claude Code 用(plugin.json, marketplace.json)
├── .codex-plugin/    # Codex 用(plugin.json)
├── skills/           # スキル本体
├── tools/            # 分野別の確認ツール(任意)
├── requirements/     # 確認ツールの依存パッケージ
├── assets/           # 検証用の JSON スキーマ
├── scripts/          # 検証スクリプト
├── docs/             # 出力見本、フィードバックの手順
└── tests/            # 自動テスト
```
