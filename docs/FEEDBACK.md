# フィードバックと改善の進め方

この文書は、配布したスキルの利用者から改善の材料を集め、スキルを直すまでの流れを定めます。

## 受付先と、誰が読めるか

- **受付先**: 試用期間中は、非公開リポジトリ `shuccii/REO` の Issue だけで受け付けます(フォーム: `.github/ISSUE_TEMPLATE/skill-feedback.yml`)。
- **読める人**: 開発者と、このリポジトリに招待された**すべての試用者**です。ほかの試用者も、あなたの Issue を読めます。
- **公開しない**: 試用期間中、Issue を外部に公開しません。リポジトリを公開するときは、受付先を非公開のフォームに移し、それまでの Issue を公開してよいかを書いた人に確認します。

## 原則

- **同意制**: 利用者が自分の判断で送る場合だけ、フィードバックを送ります。インストール時に、何を送れるかを説明します。
- **本人が確認**: 送る前に、送信内容を本人が読み、承認します。
- **最小限**: 会話の全文、ファイルの中身、研究データ、パス、個人名、所属、研究室の内部情報は集めません。
- **裏での収集はしない**: 利用者の AI セッションを、利用者に知らせずに読んだり送ったりしません。
- **人が読んでから直す**: フィードバックは開発者が読み、理由を確認してからスキルの文面やテストを変えます。利用者の入力で自動的に学習や書き換えをしません。

## 送る内容

フィードバックは `.github/ISSUE_TEMPLATE/skill-feedback.yml` の項目だけにします。

| 項目 | 例 |
|---|---|
| 対象スキル・バージョン | `research-review-workflow` / `0.6.3` |
| 役に立ったか(1〜5) | 3 |
| 何が起きたか(一般的な言い方で) | 「指摘の重大度の基準が分かりにくかった」 |
| 改善案(任意) | 「重大度を3段階にして、例を1つ添える」 |
| 確認チェック | 個人・機関・研究の内部情報を含めていないこと、改善への利用に同意すること |

## 送らない内容

- 会話の全文、途中の発言、AI の出力全文
- ファイルの中身、ファイル名、ディレクトリのパス
- 研究データ、未公開の結果、論文の草稿
- 氏名、メールアドレス、学籍番号、研究室の内部情報、非公開の規程本文

## 送信前の検査

送信内容には、次の検査をかけます(検出したら送信を止めて本人に知らせます)。

- メールアドレス、電話番号、`/Users/` や `/home/` で始まるパス
- 大学や研究室の固有名詞(利用者が登録した語を照合する)
- トークン、API キーの形式

## 改善の流れ

1. **受け取り**: Issue のラベル `feedback` で分類する。週 1 回まとめて読む。
2. **分類**: 「説明が分かりにくい」「分野の確認項目が足りない」「不具合」「誤検出」「見落とし」のどれかに分ける。
3. **再現**: 同じ条件を `tests/behavior/cases.json` に追加して、現在の版で動きを確認する。
4. **修正**: スキルの文面、Probe、スキーマ、テストのどれを直すかを決める。根拠のない確認項目は追加しない。
5. **検証**: `python3 scripts/run_checks.py` を通す。行動が変わるかは、同じ課題を旧版と新版で実行して比べる(`tests/behavior/` の手順)。
6. **公開**: 版番号を上げ、`CHANGELOG.md` に変更を書き、tag を付ける。利用者には、Issue で結果を返す。

## 「うまく働いているか」の評価

利用者の感想だけでは、AI が正しく動いたかは分かりません。次の 2 つで見ます。

- 感想: 役に立ったか、どこで詰まったか(本人の自己申告)
- 行動の比較: 固定された課題を、旧版と新版で実行して採点する(`tests/behavior/`)

## 改善モデルへの使い方

- 利用者のフィードバックは、人が読んで理由を付けた改善の材料にします。
- 利用者の会話データは、本人の同意なしに学習やファインチューニングに使いません。
- 集めたフィードバックは、上の「受付先と、誰が読めるか」の範囲だけで扱います。
